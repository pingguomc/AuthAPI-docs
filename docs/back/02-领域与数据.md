# 后端开发指导（二）——领域模型与数据

> 语言无关，行列、命名仅供参考，各团队可自行调整（如用 snake_case、加外键等），关键是**业务规则**一致。

## 绑定关系（核心）

用户的**邮箱**与 **OIDC 绑定**本质是「绑定」，可解绑，但：

- 任何时候至少要保留一种可登录方式（邮箱或至少一个 OIDC 绑定）。
- 最后一个可登录方式不可解绑；需先绑定其他方式。
- OIDC 注册且未设密码的用户，至少保留一个 OIDC 绑定。

## 角色 / 状态（两套正交概念）

- **role**（角色）：`user` / `moderator` / `admin` 三选一。`admin` 才可访问管理后台。
- **status**（状态）：`active` / `banned`。`banned_until` 可空，`null` 表示永久封禁。

要点：

- **status 不直接写入**。封禁记录是「事实来源」，`user.status`、`banned_until` 只是它的投影，由服务层在写封禁记录时同步。
- 临时封禁**惰性回写**：不用定时任务扫表，在会话鉴权/登录、查详情时若发现已过期，就地改回 `active` 即可。列表不回写，正确性靠查询条件保证。
- 所有返回 `status` 的接口都返回「计算过期后的有效值」，调用方不必自己比较时间。

## 一张用户维度的事实表设计

以「用户 + 封禁记录 + OIDC 绑定」为核心，设计大致如下（列名、类型可按需调整）：

**user（用户）**

| 列 | 说明 |
|:---:|------|
| `id` | UUID 主键，不可改 |
| `email` | 可空（OIDC 注册可无）；非空字符串；可改；UNIQUE |
| `password_hash` | 可空；非空字符串；可改；BCrypt |
| `display_name` | 可改 |
| `role` | `user`/`moderator`/`admin`，默认 `user` |
| `status` | 投影字段，禁止直接写 |
| `banned_until` | 可空；`null` 永久封禁 |
| `last_login_at` / `last_login_ip` | 可空 |
| `register_ip` | 可空 |
| `created_at` / `updated_at` | 时间戳 |

**oidc_record（OIDC 绑定）**

| 列 | 说明 |
|:---:|------|
| `id` | 主键 |
| `user_id` | → user.id |
| `provider_id` | 如 `google`、`github` |
| `issuer` | OIDC Issuer |
| `subject` | 该 Issuer 下唯一标识 |
| `email` / `username` | 可空 |
| `created_at` / `updated_at` | 时间戳 |

约束重点：

- `(issuer, subject)` 全局唯一，只能绑一个用户。
- 一个用户对同一 provider 只绑一次。
- 登录时 `(iss, sub)` 已存在 → 直接登录；否则自动注册 + 建立绑定。

**ban（封禁记录）**

| 列 | 说明 |
|:---:|------|
| `id` | 主键 |
| `user_id` | → user.id |
| `banned_until` | 可空；`null` 永久封禁 |
| `reason` | 可空 |
| `operator_id` | 操作者 |
| `created_at` | 时间戳 |

要点：同一用户同时只允许**一条生效中**封禁记录；改时长先删旧再建；解封即物理删除该记录并把 user 改回 `active`。

**audit_log（审计日志，只读）**

| 列 | 说明 |
|:---:|------|
| `id` | 主键 |
| `operator_id` | 操作者（可空） |
| `action` | 动作标识，如 `user.ban`、`user.role_change`、`user.session_revoke`、`user.ban_delete` |
| `target_user_id` | 操作对象（可空） |
| `result` | `success` / `denied` 终态 |
| `ip` | 操作者 IP |
| `payload` | 动作相关参数（结构化） |
| `created_at` | 时间戳 |

审计写入规则：**先写审计、后做业务**，审计写失败则整体失败；`result` 只记 `success`/`denied` 不回填；只记鉴权层面的拒绝（权限不足、角色不符等），普通 400/404 不记。

> 会话、邮箱验证码等**时效性强**的数据不进数据库，存在缓存（见文件三）。

## 领域实现提示

- 解绑、改绑定前检查剩余可登录方式，守住「至少一种」这条规则。
- OIDC 绑定在新用户注册、绑定时要多处配合，避免出现「无任何登录方式」的用户。
- 数据库为 `email`、`(issuer,subject)`、`(user_id,provider_id)` 建唯一约束，从底层兜住规则。
